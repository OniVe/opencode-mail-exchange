# Принятые риски

## M7 (закрыт 2026-10-23)

Отмена in-flight EWS-запроса реализована: `context.signal` из tool-execute → `MailService.run` → `AsyncLocalStorage` → собственный `MailXhrProvider` (`src/xhr-router.ts`); отмена возвращает `EWS request cancelled`, в том числе когда `ews-javascript-api` пересобирает ошибку в `SoapFaultDetails` и теряет `code` (распознаётся по `signal.aborted` + тексту). Покрыто тестами `xhr-router` (abort висящего запроса, в том числе через установленный API) и `service` (обе формы ошибки). `requestTimeoutMs` — дедлайн обычного EWS-вызова (preflight + final); для hanging-stream это inactivity-бюджет 2×`requestTimeoutMs`: watchdog сбрасывается на каждом чанке, а по тишине стрим завершается `ECONNABORTED` (плюс `signal`/`disconnect`). Двойной бюджет оставляет запас над 30-секундным heartbeat EWS при дефолтных настройках.

## Прочие риски

- Локальный индекс — plaintext SQLite; защита — ACL/BitLocker, не шифрование плагина.
- `ews-javascript-api` полу-поддерживается (последний релиз — 0.15.3, 2024-05-13); обновления проверять отдельно.
- Отмена запросов и NTLM выполняются собственным `MailXhrProvider` (`axios` + `@ewsjs/ntlm-client`): глобальный патч CJS-axios и `createRequire` удалены. Провайдер делает NTLM preflight + final request (два HTTP round-trip на EWS-вызов, как и прежний `@ewsjs/xhr`); preflight пока не кэшируется, при 401 на final выполняется один повторный handshake. Прямая зависимость `@ewsjs/xhr` удалена; транзитивная остаётся через `ews-javascript-api` и загружается его `XHRFactory` (дефолт не используется, только при пропуске `installXhrRouter`). `disconnect()` (вызывается EWS для висящей подписки) прерывает stream-запросы только текущего аккаунта; без ALS-контекста — no-op; обычные запросы и чужие аккаунты не затрагиваются. Multi-scheme `WWW-Authenticate` (`Negotiate, NTLM <token>`) обрабатывается. Заголовки фрейминга/хоста/Auth задаёт только провайдер. `xhrStream` не буферизует тело (прогресс идёт чанками, UTF-8 не рвётся на границах), non-200 читается до 64 KiB для SOAP-fault с флагом `truncated`; таймаут стрима — inactivity-watchdog 2×`requestTimeoutMs` (сбрасывается чанками), поэтому молчащая подписка завершается, а живая — нет; при тишине non-200 сохраняются статус, заголовки и частичное тело с `truncated=true`.
- Контрактные ограничения провайдера: если `timeoutMs` не передан (прямой вызов `MailXhrProvider` вне `MailService`), у стрима нет inactivity-бюджета — штатный путь всегда передаёт `requestTimeoutMs`. Ответ без тела различается по стадии: если ответ ещё не начался, сбой даёт `ECONNABORTED`/`ECONNRESET` без HTTP-статуса; если заголовки уже получены, а тело не началось, через 2× inactivity 200-стрим завершается `ECONNABORTED` (на `allowRedirect`-пути возможен `ECONNRESET` из-за гонки с follow-redirects), а non-200 — mapped-статусом с пустым телом и `truncated=true`; при наличии хотя бы одного байта сохраняются статус, заголовки, частичное тело и `truncated=true` (SOAP-fault всегда имеет тело).
- EWS в Exchange Online выключается (01.10.2026 блокировка, 01.04.2027 shutdown); для EXO нужен Graph-бэкенд (не реализован).
- `uuid` (transitive): `ews-javascript-api@0.15.3` → `uuid@9.0.1` (used as v4 without `buf`) и `@azure/msal-node@2.16.3` → `uuid@8.3.2`; обе версии формально уязвимы к GHSA-w5hq-g745-h8pq (moderate, v3/v5/v6 with `buf`), но уязвимый API в плагине не задействован. Исправление — uuid 11.1.1, вне диапазонов зависимостей. Пересмотреть вместе с R4 (форк/вендоринг `ews-javascript-api`).
- `caFile` расширяет **process-global** TLS trust store через `tls.setDefaultCACertificates`; изменение не откатывается при выгрузке плагина. Непустые встроенные корни сохраняются; отсутствующий путь — `ConfigError`, существующий нечитаемый/невалидный файл пропускается и логируется по аккаунту, остальные валидные файлы применяются. Хэш содержимого переприменяет PEM, заменённый по тому же пути, но старый корень не отзывается — он остаётся доверенным до перезапуска процесса.
- `mail_delete` с `hard: true` и `mail_empty_deleted` необратимы: EWS удаляет письма окончательно. Оба режима `mail_delete` tombstone'ят локальные строки; при soft-удалении Exchange выдаёт новый ItemId, поэтому старый id становится недействительным до sync/перечитывания `deleted`. Empty удаляет только элементы верхнего уровня, подпапки остаются. Успехом считается только `ServiceResult.Success` по каждому элементу; `Warning` и пустой `Responses` не подтверждают удаление. При полной ошибке EWS индекс не меняется; при частичной — применяются только подтверждённые удаления, вызов падает со счётчиками. Транспортная ошибка после запроса оставляет исход неизвестным — перед повтором нужен `mail_sync`.
- Гонка delete/empty с in-flight `SyncFolderItems`: синхронизация, снявшая снимок до удаления, может применить `upsertMessages` после tombstone и временно вернуть строку; состояние исправляет следующий `mail_list`/`mail_sync` по этой папке, а `mail_search` sync не запускает.
- Lazy enrichment (`BindToItems`) после ответа EWS пишет получателей/`size`/`attachmentCount` в SQLite по строкам; бюджет enrichment покрывает только ожидание EWS. При удержанной/конкурентной write-lock страница может ждать `busy_timeout` на строках; ошибки записи не фатальны и повторяются на следующей странице.

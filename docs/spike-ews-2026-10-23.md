# Spike EWS: живая проверка (23.10.2026)

**Среда:** `<ews-host>`, ящик `<mailbox>`, логин `<DOMAIN>\<user>`.
**Клиент:** Bun 1.4.2 на Windows, `ews-javascript-api` 0.15.3 + `@ewsjs/xhr` 3.1.3.
**Пароль в файлы не записывался** — только `EX_USER`/`EX_PASS` в окружении процесса.

---

## 1. Что за сервер

```
GET https://<ews-host>/EWS/Exchange.asmx  (без авторизации)
HTTP/1.1 401 Unauthorized
Server: Microsoft-IIS/8.5
X-OWA-Version: 15.1.2507.6
X-FEServer: <fe-server>
X-OAuth-Enabled: True
WWW-Authenticate: Negotiate
WWW-Authenticate: NTLM
```

- **Exchange 2016** (build 15.1.2507.6), front-end `<fe-server>`, IIS 8.5.
- Доступны только **Negotiate и NTLM**. `WWW-Authenticate: Basic` отсутствует.

## 2. Аутентификация: Basic отключён, NTLM работает

| Проверка | Результат |
|---|---|
| `curl --basic -u ...` | **401** |
| `curl --negotiate -u :` (без Kerberos-тикета) | 401 |
| `curl --ntlm -u '<DOMAIN>\<user>:...'` | **200** |

Вывод: заявленное «Basic разрешён» на этом сервере **не соответствует конфигурации** — Basic не включён. Рабочий путь — **NTLMv2**.

## 3. TLS: Bun не доверяет внутреннему CA

`fetch`/`axios` из Bun падали при подключении к EWS: сертификат выпущен внутренним CA `<internal-root-CA>`, которого нет в bundle Bun (curl на Windows использует системное хранилище, поэтому проходил).

Наблюдаемый симптом в этом стеке — **не** `UNABLE_TO_VERIFY_LEAF_SIGNATURE`, а непрозрачный
`Exception: undefined is not an object (evaluating 'response.headers')`: `@ewsjs/xhr` (`ntlmProvider.preCall`)
не проверяет результат axios и падает на `undefined` при TLS-ошибке. Проверено 23.10.2026 снятием
`NODE_EXTRA_CA_CERTS`; тот же симптом даёт и таймаут запроса.

Решение: экспортировать корневой CA из `Cert:\LocalMachine\Root` (thumbprint `<thumbprint>`, срок до 2041) в PEM и указать `NODE_EXTRA_CA_CERTS`. После этого `fetch` и `axios` видят `401` с `WWW-Authenticate: Negotiate, NTLM` без отключения проверки TLS.

> В плагине это должно быть явной настройкой (`NODE_EXTRA_CA_CERTS` или опция `ca`), а не `rejectUnauthorized: false`.

## 5. Воспроизведение


## 6. Что это значит для плагина

1. **NTLM в Bun работает** — главный риск снят. `@ewsjs/xhr` + `ews-javascript-api` проходят весь путь без sidecar.
2. **Basic использовать нельзя** — даже если политика «разрешает», на сервере он выключен. Конфиг плагина должен поддерживать NTLM c `DOMAIN\user`.
3. **Внутренний CA обязателен** — плагин должен уметь принимать путь к PEM (`NODE_EXTRA_CA_CERTS` или `ca`), иначе TLS падает.
4. **Calendar/Contacts доступны** — EWS покрывает требование «и календарь/контакты».
5. **Отправка работает** — 478 мс на `Send`, доставка ~5 с (внутри домена).
6. **Exchange 2016 build 15.1.2507.6** — вне поддержки с 14.10.2025; риск, не блокер.

## 8. Большие вложения (draft save + read + hard delete)

| Вложение | Base64 | Save | RSS | Результат |
|---|---|---|---|---|
| 5 МБ | 7 МБ | 2.7 с | 107 МБ | OK |
| 10 МБ | 13 МБ | 14.6 с | 127 МБ | OK |
| 20 МБ | 27 МБ | 10.7 с | 113 МБ | OK |
| 30 МБ | 40 МБ | 12.2 с | 166 МБ | OK |
| 40 МБ | 53 МБ | 20.7 с | 245 МБ | OK |
| 50 МБ | 67 МБ | 15–43 с | — | **HTTP 413** |

Практический предел — **~40 МБ на вложение** (лимит размера запроса IIS/EWS, не почтовый ящик). 50 МБ отбивается 413.

> Замер сделан до появления локальной проверки в плагине. Сейчас плагин проверяет 40 МБ decoded на вложение и
> 10 вложений на письмо до EWS-запроса, поэтому 413 достижим только если локальная проверка отключена/обойдена.
Стоимость: base64 +33% к размеру, память растёт примерно в 3.5–4.2 раза от размера файла (40 МБ → 245 МБ RSS).
Draft save не проверяет `MaxSendSize`; при отправке лимит организации может быть меньше.

## 9. HTML и inline-картинки

Критично: `ews-javascript-api` пишет тело в SOAP **без XML-экранирования** (`EwsServiceXmlWriter.WriteValue`).
Если передать HTML с `<`, сервер молча сохраняет **пустое тело** (без ошибки). Проверено:

| Вариант | HTML в MIME | `Body.Text` |
|---|---|---|
| raw HTML | пусто | 0 |
| XML-escaped (`&lt;p&gt;…`) | `<p>escaped html</p>` | 180 символов |

С экранированием inline-картинка проходит весь путь:

- draft: `Content-ID: <spike-image>`, `IsInline=true`, `cid:` в теле;
- после `Send()` и доставки в Inbox: `Content-ID` и `IsInline` сохранены, тело 186 символов;
- MIME: `multipart/related`, `Content-Disposition: inline`, base64 PNG.

В плагине добавлен `escapeXml()` для subject и body (и text, и HTML).

## 10. EPA на FE EWS

- Порт 80 (HTTP) снаружи недоступен (timeout) — проверить NTLM без TLS нельзя.
- HTTPS + NTLM **без channel binding** → 200. Значит `ExtendedProtectionTokenChecking` на FE EWS **не `Require`**.
- Отличить `None` от `Allow` с клиента нельзя: обе конфигурации принимают NTLM без CBT.
- Exchange 2016 (build 15.1.2507.6) — EPA по умолчанию не включается; вероятнее всего `None`, но это вывод, не факт.

## 11. Несколько ящиков: ограничение и решение

`ConfigurationApi.ConfigureXHR` в `@ewsjs/xhr` — **глобальный** провайдер: последний вызванный `useNtlmAuthentication` перекрывает предыдущий.
Проверено: после настройки второго (неверного) аккаунта первый валидный сервис начал получать **401**.

Решение — маршрутизация по `AsyncLocalStorage`: глобальный `IXHRApi` читает текущий аккаунт из ALS и делегирует в кэшированный `XhrApi` этого аккаунта.

| Проба | Результат |
|---|---|
| valid account в ALS-контексте | 200, 2 папки |
| invalid account в ALS-контексте | 401 |
| вызов без контекста | ошибка `no account context` |

Значит несколько ящиков могут сосуществовать в одном процессе; каждый аккаунт получает свой `ExchangeService`, SQLite и `XhrApi`.

Реализовано: `src/xhr-router.ts` (ALS + кэш `XhrApi` на аккаунт, таймаут запроса из `requestTimeoutMs`) + `src/service.ts` (`MailService` с пулом бэкендов и `run(account, fn)`). Конфиг — `options.accounts[]`, у каждого свой `dataDir/<id>/mail.db`, пароль — `MAIL_PASSWORD_<ID>`.
